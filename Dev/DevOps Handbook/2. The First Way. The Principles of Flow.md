The first way requires the fast and smooth flow of work.
We optimize for this **global goal** instead of local goals.
We increase flow by making **work visible.**
Our goal is to decrease the amount of time required for changes to be deployed into production.

## Make Our Work Visible
Work can bounce between teams endlessly due to incomplete information.
To help us see where work is flowing well and where work is queue, we need to use **visual work boards**. With them, we can manage our work and helps surface unnecessary handoffs in our work.

## Limit Work in Process
Daily work becomes dominated by the priority du jour. However, **interrupting** technology workers is easy because the consequences are invisible to almost everyone, even though **the negative impact to productivity may be far greater** than in manufacturing. For instance, an engineer assigned to another project incurs all the costs of having to reestablish context, as well as cognitive rules and goals.
Studies have shown that the time to complete even simple tasks, such as sorting geometric shapes, **significantly degrades when multitasking.**
We can limit multitasking by **enforcing WIP limits**. Also, it makes it easier to see problems that prevent completion of work.

> ***Stop starting. Start finishing.***

## Reduce Batch Sizes
Large batch sizes result in long lead times and poor quality.
Steps must be performed **sequentially** before starting next feature.
Small batch sizes result in less WIP, faster lead times, faster detention of errors and less rework.

## Reduce the Number of Handoffs
To transmit code through the value stream requires multiple departments to work on a variety of tasks. 
Each time the work passes from team to team, we require all sorts of communication. 
Each of these steps is a **potential queue where work will wait** when we rely on resources that are shared between different value streams. 
Even under the best circumstances, some **knowledge is inevitably lost** with each handoff. The work can lose the context of the problem or the organization goal. For instance, a server administrator may see a newly created ticket requesting that user accounts be created, without knowing what application or service the accounts are for, why then need to be created, what all the dependencies are, or whether the user account creations are actually recurring work.
To mitigate these types of problems, we strive to reduce the number of handoffs by **reorganizing teams so they can self-service** instead of having to be constantly dependent of others.

## Continually Identify and Elevate Our Constraints
### Five focusing steps
1. Identify the system's constraint
2. Decide how to exploit the system's constraint
3. Subordinate everything else to the above decisions
4. Elevate the system's constraint
5. If a constraint has been broken in the previous steps, go back to step one but do not allow inertia to cause a system constraint
### Constraint usually follows:
- **Environment creation:** wait weeks or months for production or tests environments. Create self-service environments.
- **Code deployment:** each our production code deployments takes weeks or months to perform. Automate our deployments as much as possible.
- **Test setup and run:** every code deployment requires a lot of time to set up and execute all tests. Automate testing as much as possible.
- **Overly tight architecture:** Every time we want to make a code change we have to send our engineers to scores. of committee meetings in order to get permission to make our changes. The solution is more autonomy.

## Eliminate Hardships and Waste
Eliminate waste involves reducing hardship and drudgery in our daily work through continual learning in order to achieve organization's goals.
Everything that causes delay for the customer, such as activities that can be bypassed without affecting the result are waste.

### Seven categories of waste
1. **Partially done work:** becomes obsolete and loses value as time progresses.
2. **Extra processes:** add effort and increase lead times.
3. **Extra features:** add complexity and effort to testing and managing functionality.
4. **Task switching:** requires context and manage dependencies between work.
5. **Waiting:** Increase cycle time and prevent the customer from getting value.
6. **Motion:** Move information or materials for one work center to another. Requires additional communication to resolve ambiguities. 
7. **Defects:** Incorrect, missing, or unclear information, materials, or products.
